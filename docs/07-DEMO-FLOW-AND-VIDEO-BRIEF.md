# Demo flow and motion graphic handoff

The project owner owns the backend, demo application, and final motion graphic video. This document supplies the operation plan, capture list, and optional narration/animation cues. No video, app, or screen recording is generated by this handoff.

## Story

**A participant contributes to a study. An assistant needs restricted data to do useful work. The head researcher supports the request, but cannot alone commit the demonstrated protected grant. Independent approval enables that work while identifiers remain restricted.**

The benefit is useful collaboration with scoped authority. Keep the dashboard mechanics subordinate to that story.

## Preparation by the backend/demo owner

1. Pass G1–G5 in the [integration plan](04-TECHSTACK-AND-TIDE-INTEGRATION.md).
2. Prepare five real demo identities: participant, assistant, head researcher, data steward, ethics representative. Three are governance administrators; they are not just UI labels.
3. Seed one synthetic study, an internal protocol, a coded response, and a separately protected identity payload. Participant and intended research access must use the verified sharing path.
4. Establish a repeatable starting state: assistant has only baseline internal access; the grant to be demonstrated is not active; no old pending request is mistaken for the new one.
5. Prepare separate browser profiles/windows and sign in before capture. Use existing verified Tide console links. Keep credentials and account recovery material off screen.
6. Confirm the local demo app route, provider connectivity, source labels, and actual quorum configuration. These documents do not supply a runnable URL.

Reset must be deliberate and scoped to the demo realm/database. Resetting SQLite alone cannot undo a committed Tide grant. Revoke/reseed through supported governed operations or use fresh fixtures/accounts/resources and verify the starting denial again. Do not write a broad destructive reset or bypass real approval to simplify capture.

| Step | Operator action | Expected evidence |

| 1 | Open Landing page | Product purpose, participant/research entries, synthetic-data label |
| 2 | Open participant User UI | Own contribution and stated sharing scope; no other participant records |

| 5 | Request RESTRICTED study/category access | Request scope and reason; no immediate access |
| 6 | Head proposes exact mapped grant and approves once in Tide | Correlated change ID; pending below required quorum |
| 7 | Assistant retries before quorum | Still denied under the tested path |
| 8 | Second governance administrator approves | Real commitment; source-labelled update |
| 9 | Assistant refreshes authorisation and retries | Intended protected content successfully decrypted |

| 11 | Open evidence detail | Authentic provider reference and application events distinguished |

If a step fails, preserve the evidence and fix the corresponding integration. Do not replace the failure with an unlabelled simulated result. If grant scope is study/category, say it includes that category in the study rather than implying a single-record permission.

## Two-minute edit plan

This is an editorial timing proposal, **not a latency benchmark**. The final video can cut between authenticated sessions and condense waiting while preserving the real sequence. Mark substantial wait compression where it could imply instant provider behavior.

| Time | App footage / graphic | Suggested narration | Motion or editor cue |
|---|---|---|---|
| 0–12 s | Diagram of participant and research team | “Research needs collaboration. Participant data needs controlled access.” | Draw a record moving toward a research team; highlight the trust boundary |
| 12–25 s | Landing → participant User UI | “ResearchVault gives participants a place to see their contributions and understand their sharing scope.” | Frame the participant contribution; label Synthetic study |
| 25–40 s | Assistant opens protocol, then restricted record | “An assistant can work on assigned material, but cannot open restricted responses yet.” | Hold on actual denial; avoid showing a fake decrypted preview |
| 40–55 s | Access request dialog | “They request the restricted dataset for a specific research task.” | Highlight study, category, and reason rather than sensitive content |
| 55–75 s | Head proposes/approves; pending state; denied retry | “The head researcher can propose the grant. One approval is still insufficient.” | Show one administrator approval separately from network nodes |
| 75–95 s | Second administrator and real committed status | “An independent administrator reviews the same change. The required quorum commits it.” | Connect the two actual approvals; show authentic status/reference |
| 95–110 s | Refresh, protected response opens; identity stays locked | “The assistant can now do the permitted work. Participant identifiers remain restricted.” | Reveal only synthetic content; contrast category states with text/icons |
| 110–120 s | Product benefit and scope caption | “Research can move forward without giving one researcher all the power.” | End card: verified workflow, synthetic data, TideCloak integration |

The narration is a draft. Replace claims with the narrower observed behavior if implementation differs. Do not say participant consent is cryptographically enforced unless that separate feature is verified.

## Capture list for frontend coworker(s)

- Clean Landing page at desktop recording size.
- Participant study and own-record views.
- Assistant dashboard with safe metadata and locked categories.
- Access-request dialog and actual request details.
- Pending/committed views with real source and provider reference.
- Successful restricted viewer and continuing identity denial.
- Secondary evidence view and readable empty/error states.

Provide stable framing and readable type. Avoid spinning dashboards, excessive animated backgrounds, fake real-time metrics, or several page transitions during an important state. The owner adds motion graphics; frontend does not need to become a motion-design engine.

## Animation accuracy

Do not animate a complete master decryption key travelling through the app server. Show protected capability being exercised through Tide without pretending the visual is a literal packet trace.

Two human administrator approvals and Tide's network-node threshold are different layers. A two-of-three admin demo is not two-of-three cryptographic network nodes. Only draw the specific node count if it is both necessary and verified for the deployed configuration.

An animation can explain why the integration matters; it cannot serve as evidence that decryption or governance occurred. Use app/console footage for that proof and graphics for the explanation.

## Fallback recording rules

- If switching five personas takes too long, capture each genuine session separately and edit the sequence.
- If the custom approval UI is unfinished, show the real Tide console; do not recreate an unbacked approval screen.
- If the provider is unavailable, use previously captured genuine footage labelled as a recording. Do not label replay as live.
- If shared decryption is not functioning, state that limitation and narrow the claimed demo. A prefilled plaintext viewer is not a successful protected read.
